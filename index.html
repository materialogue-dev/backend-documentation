What is Materialogue?

Materialogue is a product catalog and project management platform built for architects and interior designers in India. It lets designers browse curated catalogs of building materials (tiles, sanitary ware, paints, fabrics, lights, and more), organize those materials into projects, and generate professional export documents to share with clients and vendors.

This backend API powers all of that — from user authentication, to the product catalog with smart filtering, to PDF and Excel generation for client-ready documents.

What this backend does

  • Authentication — Email-based signup with OTP verification, JWT tokens for session management
  • Product Catalog — 100+ fields per product, smart cross-filtering, category-based attribute system
  • Project Management — Projects contain spaces (like "Master Bedroom"), each space holds selected products
  • Export Generation — Professional Order Sheets, Selection Sheets (HTML and PDF), and Excel spreadsheets
  • Team Collaboration — Company workspaces with admin/employee roles
  • Brand System — Public brand pages, contact forms, and a Brand Partner API for brands to manage their own data
  • Notifications — Admin-to-designer notifications with state-wise targeting, email delivery, and analytics
  • Custom Products — Designers can add their own products when something isn't in the catalog

Layer by layer

  • app.js — The entry point. Sets up Express, CORS middleware, and mounts all route groups at their base paths (e.g. /auth, /customer, /admin, /products).
  • Routes — Map HTTP methods and URLs to controller functions. For example, POST /auth/signup maps to authController.signup.
  • Middleware — Sits between routes and controllers. Two types: verifyToken (checks JWT for logged-in users) and brandApiKey (checks X-API-Key header for brand partners).
  • Controllers — Where all the business logic lives. Each controller file handles one domain (auth, products, projects, exports, notifications, etc.).
  • Models — Mongoose schemas that define the shape of data in MongoDB. They also handle validation (required fields, enums, max lengths).
  • Utils — Shared utilities like the database connection, file upload helper (DigitalOcean Spaces), JWT verification, and Swagger specs.

How authentication works

The API uses JWT (JSON Web Tokens) for authentication. When a user logs in, the server creates a signed token containing the user's email and ID. The frontend includes this token in the Authorization header of every subsequent request. The verifyToken middleware decodes the token and attaches the user info to the request.

For brand partners, authentication is simpler — they include their API key in the X-API-Key header, and the middleware looks up which brand the key belongs to.

User Journey

Here's how a typical designer uses the platform, and which parts of the backend power each step:

1
Sign Up & Verify

Designer submits their name, email, and password. The backend creates a temporary user record and sends a 6-digit OTP to their email. Once verified, the temporary record becomes a permanent User and a Company workspace is automatically created.

POST /auth/signup → POST /auth/verify

2
Browse the Catalog

The designer explores products by category (Tiles, Sanitary, Paints, Fabrics, etc.). They can filter by brand, color, finish, size, price range, and more. The cross-filtering system dynamically narrows available options based on current selections — if they pick "Kohler" as a brand, colors update to show only Kohler's available colors.

POST /products/withFilters

3
Save to Wishlist

Products they like can be saved to a personal wishlist for quick access later.

POST /customer/wishlist/add/:productId

4
Create a Project

When starting work on a client's home or office, the designer creates a project with the client's details (name, address, contact info). Each project acts as a container for all the material selections for that site.

POST /customer/projects

5
Organize into Spaces

Inside a project, the designer creates spaces — like "Master Bedroom", "Kitchen", "Bathroom 1", "Living Room". Each space represents a physical area in the project.

POST /customer/projects/:projectId/spaces

6
Add Products to Spaces

The designer assigns products from the catalog to each space — tiles for the bathroom floor, sanitary ware for the basin area, paint for the bedroom walls. They set quantities and track everything in one place.

POST /customer/projects/:projectId/spaces/:spaceId/products

7
Generate Exports

When ready to share with the client or place orders, the designer generates professional documents: a Selection Sheet (visual product cards for client approval), an Order Sheet (tabular format for vendors), or an Excel spreadsheet (for detailed pricing). These can be customized with theme colors.

GET /.../exports/:exportId/selection-sheet/pdf

How Models Connect

The data model is centered around Users, Projects, and Products. Here's how everything relates:

User ↔ Company

Every user belongs to a Company (workspace). When a user signs up, a Company is automatically created for them. Additional team members are added as Users with company pointing to the same Company. The Company admin field points back to the admin User.

User → Project → Space → Product

A User creates Projects. Each Project contains Spaces (embedded subdocuments). Each Space contains Products (also embedded). Products reference the catalog Product model by ID, plus store quantity, unit overrides, and custom notes.

Project → Export

Exports are embedded inside Projects. Each Export records which products to include and stores URLs for the generated PDF and Excel files. The export templates pull live product data when rendering.

Product ↔ Brand

Each Product has a brand (string, for display) and a brandId (ObjectId reference to Brand). When products are created or updated, brandId is auto-populated by matching the brand name against the Brand collection.

User → Wishlist → Product

The User model has a wishlist array of Product ObjectIds. Adding/removing from the wishlist updates this array directly on the User document.

Notification → NotificationReceipt → User

When an admin sends a Notification, a NotificationReceipt is created for each recipient User. Receipts track delivery, read, and click timestamps. Analytics are computed live from receipts.

Brand → BrandContact

When someone submits a contact form on a brand's page, a BrandContact document is created linking the submission to the Brand.

TempUser → OTP → User

During signup, a TempUser and an OTP are created together. Once the OTP is verified, the TempUser is promoted to a permanent User, and both temporary records are deleted.

Category Model

Categories define the taxonomy used to organize the product catalog. The system uses a three-level hierarchy that matches how building materials are naturally classified.

File: models/Category.js

Structure: Category → SubCategory → SubSubCategory

Cross-Filtering System

The POST /products/withFilters endpoint uses a cross-filtering approach that keeps filter options relevant and useful. Instead of showing every possible value for every filter, it dynamically narrows options based on what's currently selected.

The problem it solves

Without cross-filtering, a user might select "Kohler" as a brand and still see "Blue" in the color filter — even though Kohler has no blue products. That leads to empty search results and a frustrating experience.

How it works

1
Start with the base set

Filter products by category and subcategory to get the base product set.

2
For each filter, exclude itself

When computing available values for the "brand" filter, apply all other active filters (color, price, etc.) but NOT the brand filter itself. This way, the brand dropdown shows all brands that have products matching the other criteria.

3
Omit empty filters

If a filter has zero available values after cross-filtering, it's removed from the response entirely.

4
Compute price range

The min/max price range is also computed from the filtered set (excluding price constraints), so the price slider always reflects the actual available range.

Example

User is browsing "Sanitary > Basin Area" and selects Brand = "Kohler":

// The "color" filter values are computed from all Basin Area products
// where brand = "Kohler" (but the brand filter itself is NOT applied
// when computing brand options, so all brands with Basin Area products
// still appear in the brand dropdown)

filters: {
  brand: ["Kohler", "Jaquar", "Hindware"],  // All brands with basins
  color: ["White", "Chrome", "Biscuit"],      // Only Kohler's colors
  finish: ["Gloss", "Matte"],                 // Only Kohler's finishes
  // "size" omitted — Kohler basins don't have size data
}
Performance: Product normalization (lowercase, trimmed) is pre-computed once per request. Search results are cached and reused across all filter computations to avoid redundant work.

Notification System Architecture

The notification system lets admins communicate with designers across the platform. It supports targeted delivery (by state), dual channels (in-app + email), and provides detailed engagement analytics.

Complete Flow

1
Admin creates a draft

Sets category (Traffic Generator or Advertorial), writes the message (max 280 chars), selects target states, and chooses delivery channels.

2
Admin previews the audience

The preview endpoint queries users by state (checking both registered and shipping addresses) and returns the recipient count with state/city breakdown — before anything is sent.

3
Admin sends the notification

A NotificationReceipt is created for every matching user (with their state/city at send time). If email channel is enabled, emails are fired asynchronously via the EMAIL_WEBHOOK_URL — failures are logged but don't block the response.

4
Designers see notifications

The frontend polls /customer/notifications to show the user's notification list. Deleted notifications are automatically hidden. Each notification includes read/click status.

5
Engagement is tracked

When a user reads a notification or clicks its link, the receipt is updated with timestamps. Admins can view live analytics showing read rates, click rates, and geographic breakdown.

6
Admin can retract

Any notification (draft or sent) can be deleted. Sent notifications are soft-deleted — hidden from designers but analytics data is preserved for the admin.

Validation Rules

  • Traffic Generator category requires a link (it's meant to drive traffic somewhere)
  • At least one target state must be selected
  • Message max 280 characters
  • Only draft notifications can be edited or sent
  • Any notification (draft or sent) can be deleted/retracted
  • Default listing excludes deleted notifications — pass ?status=deleted to see them

PDF Proxy Fallback

PDF generation uses Puppeteer (headless Chrome) to render HTML templates and convert them to PDF files. This works great on servers with Chrome installed, but some deployment environments don't have the necessary system libraries.

The solution: a transparent proxy fallback that lets the same codebase work everywhere.

How it works

1
Try local Chrome

When a PDF is requested, the server first tries to launch Chrome locally using Puppeteer.

2
If that fails, proxy the request

If Chrome can't launch (missing libraries), the request is forwarded to PDF_PROXY_URL (defaults to materialogue-backend.replit.app), which has Chrome available.

3
PDF streams back

The proxy server generates the PDF and streams it back to the original caller. The end user never knows the proxy was involved.

Configuration: Set the PDF_PROXY_URL environment variable to point to a deployment with Chrome installed. The Replit deployment always has Chrome available.

Protected Routes

The ProtectedRoute component wraps routes that require authentication. It checks for a token in localStorage — if missing, the user is redirected to /login.

const ProtectedRoute = ({ children }) => {
  const token = localStorage.getItem("token");
  if (!token) {
    return <Navigate to="/login" replace />;
  }
  return children;
};

Currently protected: /wishlist, /custom-products, /projects/:project_id?, /projects/:project_id/exports.

Note: Some pages like /profile and /notification are not formally protected at the route level but depend on user data from Redux — they'll show empty content if not logged in.

Enforced in both signup and password reset forms via inline validation:

  • Minimum 8 characters
  • At least one uppercase letter
  • At least one lowercase letter
  • At least one number
  • At least one special character from: @$!%*?&#

A PasswordRequirements component (src/components/PasswordRequirements/) provides real-time visual feedback showing which criteria the entered password satisfies.

Axios Interceptors

File: src/utils/axiosConfig.js

Two interceptors are configured globally on the Axios instance:

Request Interceptor

Automatically attaches the JWT token from localStorage to every outgoing request as an Authorization: Bearer <token> header.

Response Interceptor

Handles error responses globally:

  • 401 Unauthorized — Clears localStorage, shows a "session expired" toast, and redirects to /login after 1.5 seconds. Skips this logic for auth endpoints (login/signup/verify) to avoid redirect loops.
  • 403 Forbidden — Shows a "no permission" toast message.
Duplicate prevention: A isLoggingOut flag prevents multiple toast notifications and redirects from firing simultaneously during a 401 cascade.

How Filtering Works

1
Category Selection

User hovers on a category in ProductNavigation and clicks a sub-sub-category. This updates URL query parameters via the useQueryParams hook.

2
Filter Application

Selecting filter values (brand, color, etc.) in the FilterMenu also updates query params. The Dashboard component watches for query param changes.

3
API Request

On any change, GetFilteredProducts is dispatched which calls POST /products/withFilters with the current category, filters, page, and sort parameters.

4
Cross-Filtered Response

The API returns matching products AND updated filter options. If selecting "Kohler" as brand means no "Blue" products exist, "Blue" won't appear in the color filter. The FilterMenu re-renders with the narrowed options.

Moodboard

A drag-and-drop visual canvas editor where designers create material presentation boards. Accessed at /mood-board/:mood_board_id?.

Files: src/components/MoodboardComponent/

  • Canvas — The main drawing area where products and images can be placed
  • Draggable Items — Products from projects can be dragged onto the canvas and positioned freely using react-dnd
  • Image Library — Browse and add images from the product catalog

RBAC System

The frontend implements Role-Based Access Control through utility functions in src/utils/rbacUtils.js. These functions determine what actions a user can perform on projects based on their user type and assigned permissions.

Permission Resolution

  • Company admins — Always get "owner" permission on all projects
  • Individual users — Get "owner" on projects they created
  • Company members — Permission is looked up from the project's permission array, matching by user ID or email. Only see projects where they have explicit access.

Styling Architecture

The application uses a hybrid styling approach combining Tailwind CSS utility classes with SCSS module stylesheets.

Tailwind CSS

  • Configuration — tailwind.config.js with custom theme extensions
  • Usage — Primarily used for layout, spacing, flexbox/grid, typography, and responsive utilities directly in JSX
  • Plugins — tailwindcss-animate for animation utilities, tailwind-scrollbar-hide for hidden scrollbars
  • Merge Utility — tailwind-merge via cn() helper in src/lib/utils.ts for conditional class merging
